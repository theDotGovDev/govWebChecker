# govWebChecker

Independent, outside-in measurements of US government websites — how available
they are, how fast they respond, and whether a website exists at all — published
with the method behind every number.

**📊 The site: <https://thedotgovdev.github.io/govWebChecker/>**

## What it does

Two tiers of measurement, two different questions:

- **Hourly tier** — the most-visited federal websites (selected by measured
  public traffic), checked every hour. Answers questions about short
  interruptions and response time.
- **Census tier** — every registered US `.gov` domain, roughly 16,500 of them,
  covered as a rolling one-seventh slice per day so a full cycle takes about a
  week. Answers questions about coverage and change over months: how much of
  American government publishes a website at all, and how that moves.

Every observation is appended to a plain-text record in [`data/`](data/) —
timings, status codes, and the method that produced them. The record is the
product; the [site](https://thedotgovdev.github.io/govWebChecker/) is a reading
of it, with a page for every site we know of.

## Principles

The project measures websites it does not own, run mostly by small public
teams, and publishes claims about named institutions. The
[constitution](.specify/memory/constitution.md) binds how that is done; the
short version:

- **Measurement, not load.** A check sends no more traffic than an ordinary
  visitor. Rate limits — per host, per registrable domain, and per resolved
  backend, because distinct domains routinely share one machine — live inside
  the checker where a caller cannot forget them. `robots.txt` is honored, and
  every request carries a User-Agent linking back here so an operator can see
  what the traffic is and ask for it to stop.
- **Absence is not failure.** About one registered `.gov` domain in nine
  publishes no website at all, and for some our own lookup fails. *No website*,
  *we could not determine*, and *a website that did not respond* are three
  different facts, kept apart everywhere.
- **A published number carries its method.** Every figure states what it
  counts, over what window, from how many readings, and from where. A figure
  that cannot is a build failure, not a caveat.
- **Check our working.** `npm run verify -- data/availability/<month>.jsonl`
  reads the published record — never this code — and reports whether our own
  guarantees held, so anyone can reach the same verdict without trusting us.

## Repository layout

| Path | What it is |
| --- | --- |
| [`data/`](data/) | The append-only record: one JSON line per observation, partitioned monthly |
| [`src/`](src/) | The checker, politeness limits, census machinery, and site generator — TypeScript, no runtime dependencies |
| [`targets/`](targets/) | What gets checked: the hourly target list and the census frame, both generated from published government datasets |
| [`specs/`](specs/) | Behavior specifications ([Spec Kit](https://github.com/github/spec-kit)), kept current with the code |
| [`docs/`](docs/) | Not checked in — the site is a build artifact, generated by `build-site` and deployed by Pages |
| [`ARCHITECTURE.md`](ARCHITECTURE.md) | How the pieces fit together |

Collection runs in GitHub Actions on a schedule ([`check.yml`](.github/workflows/check.yml)
hourly, [`census.yml`](.github/workflows/census.yml) daily) and commits what it
measures. Nothing here needs credentials, and nothing checks anything a normal
visitor could not reach.

## For site operators

If this project's traffic is unwelcome on a site you run, say so in an
[issue](https://github.com/theDotGovDev/govWebChecker/issues) and the site will
be removed without argument. Every page on the published site links the readings
behind it and this route.

## Development

```bash
npm ci
npm test          # node --test, against local fixtures — never real sites
npm run build     # tsc
node dist/src/cli/build-site.js --data data --out /tmp/site   # build the site locally
```

Tests never send traffic to a government site; network behavior is exercised
against local fixtures. Running the checker against real targets happens only in
the scheduled workflows, so measurements describe the targets rather than a
developer's network.
